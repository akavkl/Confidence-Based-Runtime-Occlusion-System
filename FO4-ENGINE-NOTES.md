# Fallout 4 engine notes (OG 1.10.163): a checkpoint

Everything learned about Fallout 4's engine, runtime and modding ecosystem while building CBRO, written so it can be reused for any other project on this game. It is about the game, not about the mod: how the engine culls, renders, lays out its objects, where its switches are, what other mods do to it, and how the facts were verified. Where a fact came from disassembly rather than a public header, it says so. Where something is still unverified, it says so.

Date: 2026-09-29. Game: `Fallout4.exe` 1.10.163.0 (GOG build, "OG"). Unless stated otherwise every numeric ID is an **Address Library ID for 1.10.163** (`version-1-10-163-0.bin`), every virtual address assumes the image base `0x140000000`, and every offset is a byte offset from the start of the named object or function.

---

## 1. How to read and verify these notes

### 1.1 Address Library IDs
- The 1.10.163 database is `version-1-10-163-0.bin` (V0 format): a `u64` count followed by `(u64 id, u64 rva)` pairs. Resolving an ID is a linear scan; `rva + 0x140000000` is the VA. A 12-line PowerShell script does it (read the count, loop, match).
- The IDs in `CommonLibF4-DM/include/RE/IDs.h` are namespace-qualified names for a subset of them; the IDs below that have no name there came from disassembly.
- The database matches the GOG exe: every call site used was checked to be an `E8 rel32` call and every vtable ID to resolve to its MSVC RTTI name before anything was written.

### 1.2 Tools that worked
- `dumpbin /disasm:nobytes /range:<va>,<va> Fallout4.exe` (MSVC 14.51: `D:\Softwares\Visual Studio\Product\VC\Tools\MSVC\14.51.36231\bin\Hostx64\x64\dumpbin.exe`) is a good enough disassembler for targeted reading.
- `tools/re/*.ps1` (PowerShell + C# `Add-Type`, no Python on this machine): `rtti_scan.ps1` (MSVC RTTI class names matching a pattern, with their vtable IDs), `xref_scan.ps1` / `calls_in.ps1` (callers of a function, function-bounded), `rip_refs.ps1` (RIP-relative data references to a global), `verify_offsets.ps1` (byte checks at ID + offset). `resolve_ids.ps1` and `read_rva.ps1` (bytes at an RVA, with string dereference) live in the session scratchpad.
- `NiObject::GetRTTI` (vtable slot 2) is always `lea rax, [rip+ms_RTTI]; ret`, so an object's class name can be decoded from those bytes without calling anything. Slots 3/4 are `IsNode`-style queries.
- Reading engine memory of unknown type is done under SEH (`__try`), never through virtual calls.
- **Ghidra 12.0.4 + pyghidra-mcp 0.2.7** (venv `D:\envs\fallout`, 2026-10-01). Ghidra 12's PE loader aborts on Fallout4.exe ("Function entryPoint may not be created on defined data": the data export `NvOptimusEnablement`), so the analyzed copy (`D:\envs\fo4-ghidra\Fallout4-noexports.exe`) has the export directory entry (optional header +0x70) zeroed; code and addresses are unchanged. Auto-analysis takes 13 minutes and finds 210,453 functions. `D:\envs\fo4-ghidra\fo4_analyze.py` then applies alandtse's `fo4_database.csv` (columns `id,fo4,vr,status,name`; 43,115 function names, 34,526 data labels) and labels every Address Library entry `id_<N>` (1,582,975 entries): **unnamed functions and globals decompile as `id_<N>`, the IDs these notes use.** The packed result (`Fallout4.exe.gzf`, 440 MB) imports into pyghidra-mcp without re-analysis (MCP binary name `Fallout4.exe.gzf-b076fe`; the MCP project is `<worktree>\pyghidra_mcp_projects`, excluded in `.git/info/exclude`).
- After an import, pyghidra-mcp decompiles every function in the background to build its search index (hours for 210k functions). Until that ends, `search_strings` and `search_code` refuse, and decompiles share a 2-slot pool with the indexer (30 s timeouts). `disassemble`, `list_xrefs`, `read_bytes` and `search_symbols_by_name` work at once. `D:\envs\fo4-ghidra\q.py` opens the same analysis read-only for batch work: `dec <dir> <addr|name>...` (decompile to files, then grep), `imm <callee> <reg> <imm>` and `immany <regex> <imm>` (call sites that pass an immediate, e.g. a render-target index), `refs`, `syms`, `scalar`. `findstr.ps1 <regex>` prints string VAs to feed `list_xrefs`. A folder named `ghidra` next to a pyghidra script shadows the Java package; the scripts drop their own folder from `sys.path`.

## 2. Runtime, loader and ecosystem facts

### 2.1 F4SE 0.6.23 (the OG loader)
- OG F4SE calls only `F4SEPlugin_Query` and `F4SEPlugin_Load`; `F4SEPlugin_Version` is read by the NG/AE loaders (CBRO exports all three itself since v1.26).
- There is **no trampoline interface** on OG F4SE. `F4SE::Init` allocates nothing; a plugin must create its own pool (`F4SE::AllocTrampoline(size)` in CommonLibF4RD falls back to `Trampoline::create`).
- **`F4SE::TaskInterface::AddTask` does not run on the main thread on OG.** Its queue is drained inside F4SE's hook on the engine's message-queue `ProcessTask` (`f4se/Hooks_Threads.cpp`, `MessageQueueProcessTask_Hook`), which the engine runs on its task-pool threads. Five different thread IDs were seen executing such tasks in one session. Only `AddUITask` (the `ProcessEventQueue` hook) runs on the main thread. Console commands (e.g. `tpc`) run on the main thread. Anything that must not race the render/cull code belongs in a render-stage hook or in `AddUITask`.
- F4SE messaging listeners (e.g. post-load-game) run on a message-handler thread, not the main thread.
- F4SE logs land in `%USERPROFILE%\Documents\My Games\Fallout4\F4SE\` even with MO2 profile-local settings.
- `RE::Main::GetSingleton()->threadID` is the main thread; `RE::Main::WorldRootCamera()` is the world `NiCamera`.
- **CommonLibF4RD (since CBRO v1.26):** engine ids resolve through `Data/F4SE/Plugins/f4rd-runtime.bin` (MO2 mod "Runtime Database"; the file is not on the fork's GitHub releases). `REL::ID(OG, NG, AE)`: one argument is the AE id, so OG-only ids must be written `REL::ID{ og, REL::ID::INVALID_ID }` (CBRO: `Engine::OG(id)`); on OG the resolver first tries the AE id in the runtime table, then the OG id. The RD `RE::VTABLE::*` arrays repeat the OG number as the AE id. Its RE headers are the original CommonLibF4 layout: no `BSGraphics::State`, `NiLight`, `TES`, `GridCellArray`, `EXTERIOR_DATA`, `NiCullingProcess` bodies (src/Engine/Compat.h carries the DM layouts). Resolution failures log "F4RD FAIL <id> <reason>"; a `CBRO.trace` file next to the DLL records every id requested.

### 2.2 Hooking rules learned the hard way
- **Never write data into code pages.** Counters placed inside the executable trampoline page, next to hot gateways that every culling thread runs, caused self-/cross-modifying-code machine clears: frame time went 2-3x in every mode (v1.14: 31 FPS instead of 151).
- Function-entry detours: verify the exact prologue bytes first (another plugin may have patched the entry), relocate whole position-independent instructions (`Block::Add` starts `48 89 5C 24 08`, which relocates cleanly), keep a gateway.
- A hook that must be removable at run time can be swapped with one 8-byte compare-exchange (entries are 16-byte aligned) so a thread mid-entry sees one complete version or the other; a hook another plugin stacks on top later makes the swap fail and is never undone.
- A mid-function `jmp rel32` patch must sit inside one 8-byte word (`src % 8` is 0 or 1) to be swappable atomically; replaced instructions are repeated in a stub in the trampoline.
- Call-site wrappers (`write_call` on `E8 rel32`) chain cleanly with other mods' wrappers at the same site (Upscaling wraps five DrawWorld sites; both chains fire).
- **HUD messages: pass `nullptr` as the sound, never `""`** (2026-10-02). `SendHUDMessage::ShowHUDMessage` (1163005) queues the text and sound; `HUDMessages::AddQueuedMessage` (+0x16C) always calls `UIUtils::PlayMenuSound(char*)` (1227993). That function looks the name up in BGSAudio's map, keyed by the CRC32 of each sound's editor ID (148086 at 0x14082F830; `nullptr` skips the lookup). It plays a matching SOUN (type 0x12) or SNDR (0x84) through the UI output model and keeps no handle. `""` is a real lookup key: in the Fallout London profile it matched a looping water-stream sound, which then never stopped (CBRO v1.57 bug; the engine's own callers pass `xor edx, edx`).
- Water and addon-node sounds do not depend on culling: `BGSWaterAudio::Register/UnRegisterWaterAudioEmitter` (641608 / 161507) run from the `DoAddWater` / `DoRemoveWater` traversals when water 3D attaches or detaches. Addon looping sounds (`BGSAddonNodeSoundHandleExtra::UpdateLoopingSounds`, 920138) play the 20 nearest by listener distance.
- **Do not hook `IDXGISwapChain::Present`** in this setup: Upscaling's frame generation presents through a D3D12 proxy swapchain and inserts extra frames.

## 3. Threading model

- **`Main::Update` and every `DrawWorld` render stage run on the main thread** (the pre-pass, forward, depth-resolve and first-person-alpha stages all had `tid == Main::threadID`; 0 draws on other threads or deferred contexts). There is no separate D3D11 render thread like Unreal's RHI thread.
- **Culling runs on the main thread in practice**: `Block::Add` was on the main thread for 99.99% of calls (at most 62 per 600 frames elsewhere). *Correction (2026-10-01 Ghidra):* with `bCullingBatch` 0 (the London default) a culling group is processed inline on the calling thread (`BSCullingGroup` process = 1147875, a loop over its `BSCuller` blocks and `CullingJob::SubGroup` arenas) and registered by 626862 on the same thread; jobs exist only on the batched path (`CullingJob::BatchCull`: `AddGroupToBatch` 525990, job functions `BatchProcessCuller` 0x141CD10C0 / `BatchProcessNodeCuller` 0x141CD11F0). Anything that may run on the batched path must still be lock-free.
- Registration calls `BSShaderAccumulator::RegisterObject` (accumulator vtable +0x168) from the registering thread (per-block helper 389706). With `bMultiThreadedAccumulation` (default 1) the calls sit inside a `BSMTAManager` bracket. What the manager runs in parallel afterwards (`BSMTAManager::RegisterObjects` 0x142860CA0 with its `RegisterObjectTask` arrays, `JobFunc` 0x142860FA0) was not read; the `RegisterObject` calls themselves stay on the registering thread.
- Per-object work that touches shared atomics from all those threads is measurably slow (cache-line bouncing); per-thread counters summed at log time are not.
- **Messages and events vs. the game thread (Runtime Combiner run, 2026-10-02):** these messages and events do not arrive on the thread running the game:
- Cross-session frame times at the same spot vary by 6-20 ms in both modes (time of day, weather, Shadow Boost state). Only a same-session, same-view comparison means anything.

### 4.2 First-person geometry and the depth buffer
- The first-person weapon **is drawn into the main depth buffer**, with the viewport depth range switched to **[0, 0.01]**; the world uses **[0.01, 1]**. 6-8 first-person-range draws per frame happen outside the wrapped stages, 0-1 inside the pre-pass. Any depth-based test must treat `d < 0.01` as "no world surface here".
- **The pre-pass draws first person before the world** (2026-10-06, disassembly of 56596 at 0x142850CB0): the first-person accumulator `[0x146723358]` (1430301) runs at +0x2FD..+0x327 (0x14282E190, 0x14282EF70(acc, 4, 0, -1), 0x14282E300) under the first-person camera `[0x1467232F8]`; only then does the world accumulator `[0x146723350]` run at +0x358..+0x3C1 under the world camera `[0x146723238]` (0x14282EF70(acc, 4, 0, -1), 0x14282E190, 0x14282F110(acc, 0, 0), distant-object instances 0x1428306C0, 0x14282F110(acc, 1, 0), 0x14282E300). So world fragments behind the weapon fail the depth test: **no world depth ever exists behind a drawn weapon**, in any capture taken from this depth buffer. Measured (interior, same view): a drawn weapon adds 168 first-person-range draws to the pre-pass stage in both modes (holstered 1); previs total 5057 -> 5212 with no frame-time change; CBRO 2560 -> 3210 (+530 pre-pass, +110 sun-cascade stage), +0.4-0.5 ms, because CBRO can't cull behind the weapon pixels; outdoors 5590 -> 10820 and 11.5 -> 17.9 ms (sun-shadow sweeps crossing the weapon all count as needed), previs 14.0 -> 14.3 ms.
- The pre-pass's callees (disassembly, 2026-10-06): 185153 (0x141D215C0) `(camera state 600795, NiCamera*, bool, float, float)` updates the camera data and tail-calls 0x141D22F20 to set the viewport from the camera's port (+0x184); first person passes `[1098847]` and `[483683]` (1.0), the world `[417116]` and `[1384353]` (1.0). After it the pass stores the transposed `XMMatrixInverse` (1581726) of shadow state +0x760 at +0x8A0 (shadow state = the thread's renderer context `[TLS[842564]]+0xB20`, else `[33539]`, then +0x1B70). 163409 / 761249 are an accumulator's render and finish (both skip when its +0xC4 is 0; both end by setting shadow state +0xA8 = 3, +0xC0 = 0, 761249 also +0xC8 = 0, whichever accumulator ran); 1048494 `(acc, 4, false, -1)` renders pass group 4 through the batch renderer at acc+0xC8 if it holds any; 1379976 `(acc, i, false)` renders accumulator group i (0 and 1 for the world); 777723 / 338650 around the blocks are bare `ret`s. CBRO v1.69 (Hooks/FirstPersonOrder) re-runs the first-person block after the world block's 761249 (+0x3C1): 185153 for first person, +0x8A0 again, the three calls, 185153 for the world.
- **The pre-pass has a depth-only z-prepass that draws first person first too** (2026-10-06, probe stacks: every frame's first switch into the first-person viewport is 0x141D16CED (state apply) < 1491502 (0x141D12980) < 56596+0x1EC). 1491502 `(0x1461E0900 [1378294], fp camera, world camera, fp 185153 arg, 1.0, world arg, 1.0)` binds a null pixel shader and draws six lists: first person's two (counts `[163482]` / `[382658]`, entries 0x20 at 0x14611DBF0 via 0x141D1B730 and 0x48 at 0x146305300 via 0x141D1BB00) under 185153(fp camera), then the world's (`[844802]`, `[1064092]`, `[1283533]`, `[602241]`) under 185153(world camera); a call with every count 0 returns at once. 56596 sets shadow state +0xD0 = 0 around it and 1 after. Entries are appended (`lock xadd`, at most 0x4000) by 0x141D12610 from accumulator registration (0x14282D332, dl = first person); the counts are reset only at the frame's end (0x141D0B596) and by 0x141D125E0 (called from two other renderers). With a weapon drawn its first-person lists are ~as many draws as the first-person block (83 vs 86 per frame), so holding back the block alone left the weapon's depth in front of the world; v1.69's second build also holds the first-person lists (counts set to 0 for the call at +0x1E7, drawn after the capture with the world's counts set to 0).
- **Standard Z (0 = near, 1 = far), not reversed.** fo4test's linear-depth shader is `lin = f*n / (f - d*(f-n))`; ReShade's FO4 preset is `IS_REVERSED=0`.
- Linear view depth from the render camera's own numbers: `ndc = (d - 0.01) / 0.99`, `z = depthB / (ndc - depthA)` with `depthA`, `depthB` derived from the view-projection (see §4.4); `d >= 0.999999` or `ndc >= depthA` is sky/infinite.

### 4.3 Draw-call budget (immediate draws per frame, this setup)
- Daytime exterior, previs on: 900-2,900 draws; the pre-pass 330-1,030; the **sun's shadow cascades 500-1,900 (55-65% of all draws)**, drawn outside the wrapped stages into `depthStencilTargets[8]`, a 2560x2560 3-slice array.
- Same, previs off: pre-pass 6,100-6,900 (steady), shadow draws unchanged (**previs trims only the main camera**).
- Dense pier at night: ~3.5k main draws and ~13.6k point-light shadow-map draws per frame (about 80% of draws are lamp shadow maps; one shadow accumulator per lamp, 7-11 lamps per frame).
- Each spot has a floor of fixed passes (post-processing, ENB, upscaling, UI, lamps' and cascades' fixed costs) that visibility cannot lower; with almost the whole scene culled the heavy spot still ran at 13.7 ms.

### 4.4 Cameras and projection
- `BSGraphics::State` (singleton `VariantID{600795, 2704621}`) holds `cameraState` and `cameraDataCache` (a `BSTArray<CameraStateData>`, 0x250 bytes per entry). **`cameraState` after the pre-pass is often another pass's camera** (a 37 deg FOV / near-15 scope camera, cubemap cameras). The world camera's entry is the one whose `referenceCamera == Main::WorldRootCamera()`; prefer the entry with `useJitter == false`. `camViewData` has `viewProjUnjittered`, `viewDir`, `viewRight`, `viewUp`; `posAdjust` is the camera-relative offset.
- Convention verified by a self-check (a point ahead of the camera lands at the screen centre with the right/up signs correct): **`clip = (p - posAdjust) * viewProjUnjittered`, row-vector, camera-relative.**
- The view-projection decomposes exactly into eye + orthonormal basis + per-axis scales (`ndc.x = scaleX * x/z`, `ndc.y = scaleY * y/z`) + a depth curve (`ndc.z = depthA + depthB / z`, `depthB < 0` for standard Z); verified on an off-axis point each capture.
- TAA/DLSS jitter is sub-pixel; use the unjittered matrix. The jitter still moves silhouette texels between an occluder's depth and the background from frame to frame.
- Camera near/far globals: `REL::ID{57985, 2712882}` and `{958877, 2712883}` (fo4test).
- `NiCamera::viewFrustum` is at **+0x160**: `left, right, top, bottom, near, far` (floats) then `ortho` (bool). Vertical FOV is about 50 degrees at the default settings.
- `NiCamera::world.rotate` (rows vs columns) maps onto the render basis with an ambiguity: facing within ~5.7 degrees of a world axis both readings fit. The render camera can trail the NiCamera by a frame while turning: a depth frame caught mid-turn passes a ~0.8 degree axis fit yet sits off the NiCamera by that frame's turn (0.74 degrees in the v1.58 run, where CBRO's footprint self-check took it for a fault and switched turned views off; v1.59 logs such captures and whether their offset exceeds the NiCamera's last turn).
- The rotation angle between two orientations is best computed as `2*asin(||R1 - R2||_F / (2*sqrt(2)))` (exact 0 for an unchanged matrix; `acos(trace)` reads ~0.03 degrees of noise).
- **The camera sways every frame even when the player stands still** (sub-unit translation, hundredths of a degree); a "still camera" test needs a tolerance (2 units / 0.06 degrees per frame worked). Frames with a large camera jump (fast travel, load) show as >1 s frames.
- Dynamic resolution was off (ratio 1.0); under Upscaling the depth is rendered at 1280x800 in a 1280x800 texture.

### 5.1 It is not the `NiCullingProcess` virtuals

Constructors: `BSCullingProcess` 423200, `BSGeometryListCullingProcess` 125924, `BSParabolicCullingProcess` 1288195. `BSCullingProcess::cullMode` is at +0x158 (kNormal 0, kAllPass 1, kAllFail 2, kIgnoreMultiBounds 3, kForceMultiBoundsNoUpdate 4); `updateAccumulateFlag` at +0x11D; `OnVisible` is vtable +0x1C8; the accumulator restart is vfunc +0x140; the culler's finish loop appends visible entries through vfunc +0x168.

### 5.2 The real pipeline: DrawWorld cull, scene walk, culling groups, blocks, jobs, accumulators
1. **DrawWorld cull** (718911, from `Render_PreUI`+0x16A) resets its two `BSGeometryListCullingProcess` objects (globals 865470 / 1084947), initializes its culling groups with DrawWorld's camera (global 81406), and calls the **scene walk** (1138818) on the scene root (global 1327069, which is also the `ShadowSceneNode` the batched cascade path reads its light from) with `(culler, group 0, group 1, group 2, &group array, previsActive)`.
2. The walk descends the top of the graph and calls **`Group::Add(group, obj, &obj->worldBound, flags)`** (1175493).
3. A **culling group** (`BSCullingGroup`; `Add` 1175493, `AddP1` 357475, `Cleanup` 519696, `SetCamera` 260488, init-with-camera 1549363) is a non-polymorphic **0x170-byte struct with no RTTI**: six frustum planes at +0x00, a node block list at +0x98 (current block +0xD0), a geometry block list at +0x118 (current +0x150), an "owner" at +0x158 that is **the camera's `BSCompoundFrustum*`** (set by 158202; DrawWorld passes the culler's portal-graph entry +0x68, 5.6), a flag byte at +0x16A. DrawWorld's groups: **group 0 = 1117782 (shadow casters: NiAVObject flags bit 40 clear)**, **group 1 = 133326 (non-casters)**, **group 2 = 1328670 (the previs visible list)**, plus a **group array** at 459440 (`{group* data; ...; u32 count @+0x10}`). All share one owner value. **Group 3 = 731482** holds special always-draw objects with radius-1 bounds and its own camera, registers with a second accumulator (1430301) and is reprocessed by a later pass (0x142850A27). A stack-allocated group with a null owner gets ~1,000 adds per frame from the previs code earlier in the frame (probably a shadow pass).
4. `Group::Add` sorts the object into a **block** (class name `BSCuller`, kept in `BSTObjectArena<BSCuller, ...>` arenas) through **`Block::Add(block, obj, bound, startIndex)`** (1143206; -1 = fresh add, >= 0 continues a multi-instance mesh). A block is **0x3A70 bytes**: the group's planes copied in; **SoA bound packets of four at +0x60** (`x[4] y[4] z[4] r[4]`); objects at +0x2060; per-entry **result byte at +0x3060 + 5*i** and **force-visible byte at +0x3061 + 5*i**; group markers at +0x3A6C..+0x3A6E; the owner (compound frustum) copied to +0x3A60 (non-null with a non-zero op count at +0xC4 selects `BSCuller::ProcessCompoundFrustum` 0x141CCC190, i.e. authored occluders and portals, else `BSCuller::ProcessVectorFrustum` 0x141CCBDD0); the group's +0x16A flag copied to +0x3A6F; count at +0x3A68 (max 0x200 entries). Block::Add checks `BSPreCulledObjects::IsActive` (0x142809E30): **with previs active and the block's +0x3A6F flag 0, main-pass entries are marked force-visible and merge-instanced entries are not expanded**, and the finish loop (0x1CCEBF0) appends them regardless of the frustum result. *Decompiled 2026-10-03 (for Runtime Combiner):* a fresh add sets the force-visible byte to `flags bit 11 || (IsActive() && block+0x3A6F == 0)`; the instance entries of a type-0x0F mesh get bit 11 only. So an always-draw entry is visible in every pass that processes its group, previs or not.
5. **Group processing is 1147875** (0x141CCCE70, `(group, bool)`), not 626862: unbatched it loops over the blocks itself (inline, §3) and runs the SIMD test per block (skipped for blocks with no entries, or with previs active unless the block's +0x3A6F flag is set), then 558046 per block. *Read in full 2026-10-01:* with group byte +0x168 clear it first returns the child list (+0xD8) and the SubGroup arenas (+0x60) to their free lists, opens a fresh child block (+0x3A6F = group +0x16A), then processes the node list (+0x98) with **`count != 0 && (!IsActive() || block+0x3A6F)`** (`ProcessCompoundFrustum` when the block's frustum +0x3A60 has ops at +0xC4, else `ProcessVectorFrustum`) and runs 558046 on every node block; with the bool argument false it also processes the geometry list (+0x118), the child list and the SubGroups under the same gate. **A skipped block keeps the result bytes of the last pass that processed it.** 558046 (the node finish): for each entry with its result or force-visible byte set it walks the node's children into the group (`NiNode::ForEachChild` → `AddP1`), or for a `BSFadeNode` runs `BSFadeNode::OnVisible` (with the group's camera +0x160 when group byte +0x169 is set) and `AddP1FadeNode`; with +0x169 set it also sets flag bit 42 on visible entries and clears it on the others (re-read 2026-10-03: before the node handling, for every entry of the block; nothing else in 558046 writes it). *Measured (Runtime Combiner run 5, 2026-10-03):* container-member meshes (geometry entries of group 0) read bit 42 clear at `PlayerCharacter::Update` on all 1,327 of them while they were drawn, so a mesh's bit 42 is no "drawn last frame" signal at the game tick (culling-process paths clear it on objects failing their planes, 6.2 and 7.9). A childless always-draw `BSFadeNode` filed whole into group 0 is a clean one: forced visible by `Block::Add`, set by 558046 only when a main-view pass processes group 0, and never failed by the culling-process paths; **626862 (0x141CCD520, `(group, accumulator)`) registers** a processed group's blocks into an accumulator (next item). Visible nodes push their children back in through **`ChildPush`** = `BSCullingGroup::AddP1(BSGeometry*, NiBound&, bool, bool, bool, CullingJob::SubGroup*)` (357475: `(group, obj, bound, r9b flag, byte, byte, context)`, one object per call; the loop over the children is in its callers) → `Block::Add`.
6. Each view then **registers** its visible geometry with its own accumulator: **`BSShaderAccumulator::RegisterObject(BSGeometry*)`, vtable 357329 slot 45** (0x14282CED0; called only through the vtable; the RTTI shows no subclass; all four register loops ignore its result). DrawWorld's main accumulator is the global **1211381**. *Correction (2026-10-01 Ghidra):* there is no general re-test against the accumulator's camera. The block register loop (962984 = 0x141CCEBF0, called by 626862 for the geometry list +0x118 and the child list +0xD8; SubGroups through 389706) files every entry whose result byte (+0x3060 + 5i) or force-visible byte (+0x3061 + 5i) is set; only geometry of type byte 0x0A (with global 696323 set and a camera on the accumulator) goes through 324948 (0x141CC4870: its sub-bounds, `+0x170` array / count `+0x180`, tested with `BSMultiBoundAABB::WithinPlanes`), and type 0x0E through 1233902 / 461269. Merge-instanced type 0x0F entries are filed whole when any instance entry passed, and only when `!IsActive() || block+0x3A6F`. `RegisterObject` itself (decompiled 2026-10-03): with multithreaded accumulation active (1497973 && 354007) it defers the geometry through 910636; it skips geometry with no +0x148 / +0x140 and a null vtable +0x88 (except `BSInstanceGroup` and id 580676); geometry with flag bit 35 only gets property +0x60 (`lastAccumTime`) = id 1500399; the rest jumps to the render-mode handler table id 1279938[accumulator +0x560] (not read: whether those stamp +0x60). `BSShaderAccumulator::renderMode` is at **+0x560** (`BSShaderManager::etRenderMode`: 24 = the main "deferred gbuffer" pass, 0xF kShadowmap, **0x10 kShadowmapDir** (the four sun cascades), **0x11 kShadowmapPB** (one per lamp)), `shadowLight` at +0x568. Groups 1, 2 and the array register with the main accumulator only; **group 0 is also registered by the sun's cascades** (§6.1) through `CullingJob::BatchCull::AddGroupToBatch(group, bool, bool, accumulator, camera, planes)` (525990 = 0x141CD0880; 0x68-byte records `{group, camera, planes, accumulator}`; registration 0x141CCB8C0).

### 5.3 The scene walk (1138818) in detail, exterior path with previs off
- The exterior path runs when byte `[[culler+0x150]+0x138]` is set and the override-root global 0x146723208 is null. The **world node is the scene root's child 3**; each of its children from index 1 on is a **cell node** (the walk sets its flag bit 42). Of a cell node's children only **2, 3 and 9** are visited: child 2 → its children go whole into group 1 (path B, +0x4C0..+0x4F9, ~104 adds per frame); **child 3 = the cell's precombined chunks and static references**; child 9 holds precombined art whose mesh key has bit 30 set (`TESObjectCELL::AttachCombinedObjectArt`+0x69D; the cell child roles are in 5.6). The world node's child 0 goes whole into group 1; the tail adds the scene root's children 6, 7 and 10 to group 1.
- For node 3 (and 9): loop start at +0x5B8 (`cmp dx, word [rax+132h]`: the child count is a word at node+0x132; node in r14, index in r15d, cell in r12, other state in rbp/rbx/rdi/r13). For each child, +0x5F1 fetches its RTTI (`mov rax,[rsi]; mov rcx,rsi; call [rax+10h]`) and compares it with **`NiNode`'s NiRTTI (ID 191219 = 0x145C08EC0)**: an **exact `NiNode`** child ("container") has its own children added to group 0 one by one with flags 0 (loop +0x602..+0x633, Group::Add return address Fallout4.exe+0x284E581: **~5,700 adds per frame**, the main feeder); anything else is added whole (+0x635, return address +0x284E59A: ~1,340 per frame). The exact-NiNode containers under node 3 are the **precombined NIF roots**, each holding about ten `BSFadeNode` chunks. `BSMultiBoundNode`'s NiRTTI is 0x14609A070.
- The override-root path (global 0x146723208 non-null) has the same shape at +0xA00 (node in r15, index in r12d) and +0xA31 (container check with `cmp rax, rbx`). The portal/room path (`[root+0x238]`, byte `[[culler+0x150]+0x139]`) exists for interiors (read 2026-10-01, 5.6).
- DrawWorld's cull also has its **own loop over the roots registered with the culling camera** (`[[culler+0x150]+0x10]+0x58`, count at +0x68; 2026-10-01: that is the **`BSPortalGraph` always-render array** (`GetAlwaysRenderAt` reads +0x58, `GetAlwaysRenderArrayCount` +0x68), where `TESObjectCELL::AttachToPortalGraph` puts each cell's actor node and dynamic node, see 5.6; 0x14284F61C-0x14284F705, loop test at 718911+0x309): for each root that is a node and not flag-14 special it adds every child to group 0 or group 1 by the shadow-caster flag (~13 adds per frame; return address +0x284F6E5).
- **With previs on, the main view never draws group 0** (corrected 2026-10-03, Ghidra, for Runtime Combiner): the walk (1138818 = 0x14284DF50) skips the cell expansion only when `QEnabled()` (917969) is true and `sceneRoot` (1327069) +0x14C (gate A) is 0. With gate A non-zero it still fills group 0 (cell children 3/9, container members), skipping only world child 0, cell child 2 and the root child 2 subtree. But DrawWorld's cull (718911 = 0x14284F350) processes and registers **group 2 (1328670, the previs list) instead of group 0 (1117782)** while `QEnabled()`, then group 1 (133326) always, and the group array (459440) only without previs; the batched path (798015) does the same. So anything filed only in group 0 (container members such as Runtime Combiner's chunks; anything not in a previs list) is not drawn in the main view while previs is active. Its registered-root loop runs when `!QEnabled()` or gate B (`sceneRoot` +0x180) is set. Previs's own list is keyed by reference form ID and names only references in their cell's previs list; it draws the rest of what it knows as dynamic objects (5.5d). Per frame at a light exterior: previs on ~300-1,000 main-pass `Block::Add` entries and ~830 objects processed in the cull stage (0.4 ms); previs off 9,000-11,700 entries, ~7,200 top-level `Group::Add`s, ~9,700 objects (1.8-3.2 ms).
- **A cell's node 9 can be AppCulled, and previs draws its chunks anyway** (CBRO v1.67 scene scan, 2026-10-05, Fallout London, camera (-3724,-29572,-273)): the world node (scene root child 3) is named `ObjectLODRoot` and its cell nodes are `BSMultiBoundNode`s. In two of three cells in view, node 9 (bit-30 precombined art: traffic-signal heads, signs, bollards, beside a sound marker's 3D) carried bit 0; the third cell's did not. The previs-off walk skips an AppCulled node, so none of those chunks was filed in CBRO frames (they appeared only once the player got close). The writer of that bit was not found (`SetAppCulled` 1423392 is inlined almost everywhere; `AttachCombinedObjectArt` and `RegisterCombinedObjectVisibility` don't set it). CBRO v1.68 (`bCellArtNode9`) files such a node's children into group 0 when the walk starts the same cell's node 3.
- Grouping nodes (cell nodes and containers) have flags `0x80000000280E` (bit 11 always-draw set) and **an unmaintained `worldBound` (radius 1)**. The always-draw bit on such a node means "never cull me by my bound"; only the bounds of the entries the engine files (their children) are maintained.

### 5.4 Merge-instanced geometry in the blocks
- A `BSGeometry` of **type byte 0x0F** (= **`BSCombinedTriShape`**, 7.5; not the `BSMergeInstancedTriShape` class) has an instance array at obj+0x1C0 (stride 0xF0, world `NiBound` at +0xC0 of each record) and a count at obj+0x1D0. `Block::Add` writes the mesh's own entry and then one entry per instance until the block is full; the caller continues in a new block with `startIndex` = the next instance. The finish loop ignores the mesh's own entry and appends the whole mesh if any instance entry passed. Such entries were never seen in the main pass with previs off.
- **`BSMergeInstancedTriShape`** (vtable 245837, size 0x1B0) is different: the precombine builder (657056 = 0x1428444A0) concatenates several source meshes' vertices *in their own local spaces* into one vertex buffer and stores each instance's `NiTransform` (translation relative to the group centre, which becomes the node's local translate) in a GPU buffer at +0x170 (80-byte records: `NiTransform` at +0, grayscale-palette scale at +0x40; count at +0x34, kind at +0x38; LOD triangle counts at +0x1A0). **The CPU copy of those records is freed**, so the raw vertex buffer says nothing about where the instances are drawn. 16-28% of precombined leaf shapes are of this class; 85 of 218 kept meshes at one wall.

### 5.5 Previs (`BSPreCulledObjects`) internals
- `IsActive()` (917969, inlined copy at 0x142809E30) = `enabled (byte 0x146722288, ID 493183) && INI (0x1438C7890, ID 1472203) && !suspended (0x146722289, ID 718924)`; queried in 35 places.
- `SetEnabled(bool)` (1090712): **enable is only a byte write; disable runs the flush** (61939), which calls the callbacks in two registries (0x1438C78F8 keyed by reference form ID, 0x1438C7928) with `true`. `SetSuspended(bool, flush)` (1263609). The game suspends previs itself in some modes (callers 0xE9E742 and inside the cascade cull 1390075). `IsEnabled` is 652211. Console: `tpc`. Names in alandtse's database (2026-10-03): 652211 = `BSPreCulledObjects::QWantEnabled()` (0x142809E60, the enabled byte only), 917969 = `QEnabled()` (the effective state above), 1090712 = `SetWantEnabled(bool)` (0x142809E70). Its only callers (Ghidra refs, 2026-10-03) are `BSPrecomputedVisibility::InitSDM` (0x1427ACF1B, startup) and the console `tpc` (189985 +0xE), and it is the only writer of the enabled byte 0x146722288: once a plugin switches previs off, nothing in the game switches it back on except `tpc`.
- The previs feed into DrawWorld group 2 is 997287 (replaced by Addictol when present). Other previs classes seen: `BSPrecomputedVisibility::BSVisDB` (the `.uvd` loader), `MultiCellVisibilityData`, `BGSObjectVisibilityManager`, `BSPreCulledObjects::ObjectRecord{obj, flags}`, `ExtraCellPrevisRefs`, `TES::UpdateMultiBoundVisibility` {1281872, 2192134}. `TESObjectCELL` has `visibilityData`, `rootVisibilityCellID`, `visCalcDate`, `preCombineDate`.
- Previs marks hidden objects with flag bit 26 (pre-processed) and bit 39 (not visible); the lamp culler (§6.2) honours those bits, so **previs also trims lamp shadow casters** while it leaves the sun's cascades to their own path.
- Toggling previs off does not leave it degraded (enable is a byte write), and switching it on the main thread with nothing reading previs data (right before DrawWorld's cull) is safe; switching it from a worker thread races the cull.
- Previs is position-only and conservative over a cell cluster; pre-generated previs can wrongly hide objects a mod added or moved.

## 6. Shadows

### 6.1 The sun (directional cascades)
- **`BSShadowDirectionalLight`** (vtable 97945). Its **slot 14 update** (1242204 = 0x1428CACC0) normalizes **row 0 of its `NiLight`'s world rotation** (the light is at +0xB8 of the shadow light; `world.rotate` is NiAVObject +0x70), eases direction changes over time (state at +0x200/+0x210/+0x220), and builds its **shadow camera (+0x2C0)** with local rotation row 0 = that direction, **placed at `view camera - 15000 * direction`** (constant 0x14309DD00). So the shadow camera's rotation row 0 is the light's travel direction, and `(view - cameraPos) . row0 == +15000` verifies the sign at run time. The direction points down (z < 0) whenever the sun is up; observed `(-0.57, 0.62, -0.54)`.
- The cascade range is the global 777729 (0x1467333DC): `fDirShadowDistance` as applied (1000 when unset), written by 545406; slot 14 clamps the cascade far to `min(camera far, range)`.
- **The cascades are on at night too** (the moon): every exterior frame of the CBRO v1.53 run, across times of day, had the directional-shadows byte set, and the kept spot lights' group passes ran in those same frames. So with the sun "up" group 0 has three readers: the main view, the cascades and the spot lights (6.2a). CBRO up to v1.53 left a group-0 entry out when the main view and the sun didn't need it, without asking the spot lamps; v1.54 keeps such an entry while it lies within a recorded spot lamp's reach (or, with bLampGroupTrim, while a spot lamp's shadow of it may reach a visible surface).
- **Cascade cull: 1390075 (light, group 0).** With previs off it points group 0's camera and frustum at the sun's culler and **registers every cascade as another view of group 0** (four `kShadowmapDir` accumulators); with previs on it builds its own stack group from previs data instead. **So anything removed from group 0 also disappears from the sun's shadow maps** (hidden or off-screen casters lose their shadows).
- Two paths select on `bCullingBatch` (ID 938585, read as `movzx eax, byte [0x14384E778]` at 0x141CCB850) and both require the directional-shadows byte (241042):
  - batched (1): `Render_PreUI`+0x175 → 339369, which at +0x185 calls 432406 (runs the light's slot-14 update, then tail-jumps to 1390075 with group 0, `lea rdx, [0x1467233C0]`); light from `ShadowSceneNode` 1327069 +0x208.
  - unbatched (0, the London default): `Render_PreUI`+0x1BF → 1108521, which at +0xE49 calls 1390075 after `light->update(camera)` when `dirShadows && !bCullingBatch`; light from `ShadowSceneNode` 879298 +0x208.
  - 259940 is 432406's code with no caller. DrawWorld's callback slot (global 473367) holds a no-op (`ret` at 0x1403A8020, set through 0x1428579B0 from 0x140D3DA9A), so hooking it sees nothing.
- With the directional-shadows byte clear (night, interiors) neither path runs and nothing but the main camera reads group 0. The byte is fixed at `Render_PreUI`+0x0, before the cull, so whatever it says at cull time holds for the cascades that frame.
- Cascade cost: 500-1,900 draws per frame in a daytime exterior, into `depthStencilTargets[8]`. With previs on the cascades draw only previs's (small) shadow list; with previs off they draw every group-0 caster in range, including everything behind the walls in front of the camera.
- Shadow maps filter over a few texels; the direction eases over time; cascade splits run along view depth.
- **Cascade records and readers** (from Renderer Replacer's copy of these notes, 10.10, 2026-10-08; used by CBRO v1.80): `BSShadowDirectionalLight`+0x190 u32 cascade count (3 in the London profile), +0x198 the 0xF0-byte records, +0x250 float split distances (800, 3000, then the shadow distance). Record +0x48 the cascade's `BSShaderAccumulator*`, **+0x58 / +0x68 two `NiPlane`s written by slot 14 (1242204) each frame: normal = view direction through the cascade's first view depth, and normal = -view direction through its last (blend band included)**. 1390075 processes group 0 per cascade against the cascade camera's planes only (the light-space box) and registers it into the cascade's accumulator (626862, slot 45 per geometry). The deferred sun light reads each cascade by its receivers' depth; godrays (1070837) read the first min(count, u32 542491 = 2) cascades through the air of the view, so with three cascades the last is read only by surface lighting. CBRO v1.80 reads the slab at the cull begin (last frame's planes) and checks the normals (n . viewDir > 0.98 / < -0.98) and the far end against the cascade range (0.9-1.5x) before using it.

### 6.2 Point and spot lights ("lamps", paraboloid shadow maps)
- `BSShadowParabolicLight` vtable slot 9 (656208) culls a lamp's casters through `BSParabolicCullingProcess::Process(camera, scene, set)` (vtable 845854 slot 0x1A): sets the camera and frustum, restarts the accumulator (vfunc +0x140), then `scene->Cull`. Before that, its setup `0x1429775C0(culler, camera, ?, radius, flag)` (called at +0x190 with `radius = [light+0xB8]->+0x138`, i.e. `NiLight::spec.r`) puts the **light's culling sphere on the culler: centre at +0x1C0 (= the shadow camera's world translate), radius at +0x1CC (also +0x1A0)**. The shadow camera's own frustum far is 1 (the paraboloid projection is normalized), so it says nothing about the reach.
- Per-object `Process` (slot 0x19, 0x1429772B0): `cullMode` 1/2 pass/fail everything; **flags bit 11 (always-draw) passes without a test; bit 26 (pre-processed) is decided by bit 39 (not-visible)**; otherwise its frustum test (0x142977950), then `OnVisible` (vtable +0x1C8), which files geometry or walks a node's children; a failing object drops its subtree and, when culler byte +0x11D is set, has its bit 42 (accumulated) cleared.
- *Decompiled 2026-10-01:* `NiAVObject::Cull(culler)` (0x141BA4740) calls the culler's slot 0x19 for any object without flag bit 0, and `NiNode::OnVisible` (0x141B99A90) culls every child when the node's radius is non-zero or it has bit 11, so every object of the traversal reaches slot 0x19. In slot 0x19, every cull mode other than 1 and 2 tests (mode 4 included); bit 26 is decided by bit 39 **unless the culler's byte +0x11E is set**, in which case it is tested too; bit 11 passes; the test is `DoParabolicCulling` (0x142977750: `TestParabolicCulling` on the object's world bound +0xB0 against the culler's sphere +0x1C0/+0x1CC and plane +0x1B0, then OnVisible) or, with a compound frustum at culler +0x188 that has ops (+0xC4) and a mode other than 3, that frustum's `Process` as well. `BSParabolicCullingProcess::SetCamera` (0x1429775C0) writes the camera (+0x18), the plane +0x1B0 from the camera's direction, the sphere centre +0x1C0 (camera translate) and radius +0x1CC / +0x1A0. CBRO v1.52 and earlier tested casters only in modes 0 and 3 and never bit-26 ones; in the v1.52 interior run whole 600-frame intervals with ~5 region-limited lamps tested no object at all (e.g. 5.2 lights, 0 tested, ~4,000 point-light casters filed a frame). v1.53 tests exactly where the engine runs its sphere test and logs the cull modes and skip reasons. The v1.53 run (interior) showed cull mode 4 for 77% of the region-limited lamps and mode 3 for the rest (mode 0 never), so v1.52 had tested about a quarter of them; v1.53 tested 20-33k objects a frame, most of them outside the lamp's sphere, which the engine fails anyway. v1.54 runs CBRO's test only on objects that meet the lamp's sphere (the engine's own first test) and times the lamp culls.
- A lamp's shadow map matters only if a visible surface lies inside the lamp's reach. Up to v1.54 CBRO emptied a map only when the whole reach sphere was behind the depth, so in the start interior of the v1.52-v1.54 runs one far-plane Hi-Z texel (nothing drawn there: a crack into the void) inside a lamp's footprint made that lamp (-7239, 8936, 1093, reach 742) "visible" every 30-90 frames, and its map (~1,900 casters) was drawn again each time (14 spikes in 10 s while standing still). v1.55 also empties a map when every texel of the reach's screen box holds its surfaces in front of the reach or beyond it (`NoSurfaceBetween` on the nearest and farthest pyramids; far-plane texels count as beyond), logged as "hidden with no visible surface in reach". Main-view objects keep the strict behind-the-depth test. In the v1.55 run that rule held in 1 of 426 intervals and the same lamp still flipped: it scanned the reach's whole screen box, whose corners hold surfaces outside the sphere, while the behind-the-depth test only reads texels the sphere's rays pass through. v1.56 restricts it to those texels too. A level-0 Hi-Z texel spans 4x4 depth pixels: if the crack's texel also holds wall pixels (nearest < 1) no texel-level test can prove the reach empty there; v1.56's flip samples print that texel's nearest depth to tell. They did: every flip of the start-interior lamps saw one texel with farthest 1.0 (far plane) and nearest ~0.981 (a wall at roughly 790 units, in front of the lamps' reach), so a wall with a crack into the void, and the flips came and went with the camera's idle sway (the user saw the spikes stop while the console paused the game). v1.57's Hi-Z build also stores level 0's farthest *drawn* depth (the far plane left out, first person as 0, merged like the farthest depth; checked bit-exact by tools/tests/hiz_gpu_test.cpp) and the lamp test reads it at level 0 for the "in front" side. In the v1.57 run (start interior, then 26 minutes of exterior) the start-interior spikes were gone: 2 drawn-set spikes in 3.5 minutes there, both while the camera moved, against 14 in 10 s before; the empty-reach rule held in 17 of 300 intervals for point lights (up to 0.51 lights per frame) and 16 for spots (up to 1.22). With the camera moving, spikes remain: the depth is 1-4 frames old, so a fast turn uncovers a screen-edge strip with no depth yet.
- Lamp culls run **every frame per lamp** (the count of culls matches the lamp count), so no lamp shadow map outlives the view it was culled for. Shadow cameras are **pooled across lights** (the camera pointer is not a light's identity; position + reach is). Observed reach 742 units for a street lamp with `worldBound` radius 163-296. About 8k objects per frame pass through these cullers at a light exterior; at a dense night scene 11 lamps produce ~13.6k shadow draws and 15-20k registrations per frame; with previs off every object within a lamp's reach casts, previs on trims them via bits 26/39.
- Geometric fact used: for a lamp inside the view pyramid, a caster entirely outside the (slightly widened) pyramid cannot shadow a visible pixel, because the lamp-to-pixel segment stays inside the convex pyramid. Shadow filtering reaches about 5 degrees seen from the light.

### 6.3 Lights in general
- Lights live in the scene's light list, not in the culling groups: with previs off, lights never pass through the main-camera cull blocks. `NiPointLight::worldBound` radius ranged 42-4,793; `NiLight::modelBound` (+0x150) is either -1 or equal to the world bound; the actual radius is **`NiLight::spec.r` at +0x138**, often far larger than the bounds.
- Hiding a node drops the lights beneath it from lighting visible surfaces. The engine does not appear to have a "light budget" that previs protects: an earlier theory that switching previs off overran a renderer light budget was disproven (the lighting breakage came from wrong-camera rejections).

### 7.3 Cells, references, precombines
- `TES::GetSingleton()->gridCells / interiorCell`, `TESObjectCELL::references`, `LOADED_CELL_DATA::combinedObjects` at +0x1E0 holds the precombined chunks (survey: 5,738 chunks in 25 London cells; chunk bound radius mean 452 units, max 2,145, 97% under 2,048; plus 1,020 non-precombined references with their own 3D, mean radius 229). **Precombined references have no 3D of their own** (read the 3D field, do not call `Get3D()` expecting one).
- Fallout London ships 135,620 precombined NIFs and 888 previs `.uvd` files (`LondonWorldSpace - MeshesExtra.ba2`); vanilla 124,871 and 966. Precombines are draw-call batching per material, not visibility.
- Authored occlusion: `BSMultiBoundRoom`, `BSPortalGraph`, occlusion planes/boxes (`bEnableBoundingVolumeOcclusion`).
- Actors: the engine updates actor bounds every frame; an NPC walking under a node can leave the node's bound stale for a frame; hiding an actor's parts from the main camera only (not from the shadow views) does not break its shadow.
- **Static collections placed as their own meshes (precombines off): a piece's model bound need not hold its geometry** (2026-10-09, Fallout London, `bUseCombinedObjects` = 0). A SCOL reference's 3D is a `BSFadeNode` root (userData = the REFR, base form type `kSCOL` 0x25) over a `NiNode` holding the pieces (`BSTriShape` / `BSMeshLODTriShape`, vertex desc flags 0x41B: full-precision positions, no usable CPU vertex copy). In `Folon_SCOL_MCHBlockGaljero` one piece (sphere r=346, the foot of a wall next to the camera) lay 26 units outside the main frustum's left plane while its triangles were on screen; its world bound matched model bound x world transform, so the model bound itself is short. With previs off the main cull's frustum test drops such a piece; with previs on it is drawn, because previs files its list force-visible with no frustum test. With precombines on, the same geometry is part of a precombined chunk whose bound is sound.
- **Previs's main view registers objects behind the camera.** Its list entries (and its dynamic objects) are force-visible in `Block::Add`, so no frustum test runs on them: at one spot most objects previs registered that the frustum-tested path never did were behind the camera (2026-10-09, main-accumulator registrations compared over settled frames).

## 8. Engine behaviour observed at run time (numbers worth remembering)
- Light exterior, standing still: previs on 6.5 ms (cull stage 0.4-0.5 ms, ~900 pre-pass draws); previs off with no culling ~6,100-6,900 pre-pass draws.
- The main-pass cull stage with previs off is dominated by the engine filing and frustum-testing ~9,700 objects (~70-150 ns per object of any extra per-object work on the main thread adds up to milliseconds).
- Per-frame registrations at a light exterior: main view 1,560-1,660; the four sun cascades 1,436 + 1,346 + 451 + 121 (previs on: main 1,253, cascades 2,801 in total).
- Sky texels are cleared to the far plane (1.0) in the depth buffer.
- Loading, fast travel and cell transitions show as frames longer than 1 s; the engine's scene structure after a load is rebuilt (object addresses are reused).
- Hi-Z built from the pre-pass depth at 1/4 resolution (320x200) is enough to hide ~85% of the previs-off main pass at a wall; sphere bounds of large chunks are what stays ("near" objects whose spheres reach the eye plane).

### 5.5a Previs enable/disable, read from the code (2026-09-29)
- `SetEnabled(bool)` (1090712, 0x142809E70): writes the enabled byte (0x146722288); with `false`, or with the INI byte (0x1438C7890) clear, or while suspended (0x146722289), it tail-jumps to the flush (61939, 0x14280AAB0). With `true` and not suspended it returns: **re-enabling is only the byte write.**
- `SetSuspended(bool suspend, bool flush)` (1263609, 0x142809EB0): writes the suspended byte; flushes only when `flush` and (suspending, or previs not enabled/INI off). Unsuspending with previs enabled never flushes. - The vanilla visible list: a `BSTArray<u32>` at 0x1467222A8 (count 0x1467222B8, lock 0x1467222A0), appended by 1225481 (0x142809AA0, no direct caller in the exe: filled through callbacks or by Addictol), cleared by 1131946 (0x142809B10). ### 5.5b Previs is a per-frame query; the fast path and its feeds (2026-09-30 disassembly; details in PREVIS-FEED-PLAN.md section 2)

### 5.5d Previs dynamic objects: what previs draws besides its lists (2026-10-03 Ghidra, for Runtime Combiner)
- **The query has a second half.** 903843 (0x1427AE4B0, rcx = the `BSPrecomputedVisibility::MultiCellVisibilityData*` in global 787073 = 0x1458D0AA8) runs the Umbra query, fills the main list with the visible tome objects' ids (Umbra index to id: 56614, or 1372691 for a tome collection), then walks its **dynamic-object set** (a `BSTSet<NiAVObject*>` at +0xB0, capacity +0x94, free count +0x98): main view through 162587 -> 1535502 (0x1427B15B0), sun and rain through 471124 (0x1427B1670), per object 449607 (0x1427B09D0; 1406693 for sun and rain) -> 1383851 (0x1427B2210; 1301398 = 0x1427B28D0 is its twin with another Umbra test).
- **The per-object test** (1383851): skipped when the object itself is AppCulled (its own bit 0: an AppCulled parent doesn't count) or its world-bound radius (+0xBC) is not positive. An AABB from the world bound (or a multibound's box), tested by Umbra (29920; 904323 in the twin). When visible: a top fade node (bit 14 and `IsFadeNode`) gets `BSFadeNode::OnVisible(camera)` in the main view (`OnVisibleFadeInOnly` otherwise); then, if `currentFade` > 0 and `fadeAmount` > 0 (`UpdateGeomArray` when bit 29 is set), every `geomArray` entry is tested and pushed as a pool record `{geometry, entry flags | 1 when occluded}` (lambdas 781885 / 128874). Another node recurses into its children; a leaf or childless node is pushed as `{object, 0}`. The feeds skip records with bit 0 (5.5b). In the main pass 449607 then sets the object's flag **bit 42** when any of it was visible and clears it otherwise, and calls 1197955.
- **Registration.** `MultiCellVisibilityData::RegisterDynamicObject(NiAVObject*)` is 272586 (0x1427AF460), `UnregisterDynamicObject` 697930 (0x1427AF590): each appends `{object (a reference taken), 0 = add / 1 = remove}` to a pending array (+0xB8, count +0xC8) under the spin lock +0x38, from any thread. `MultiCellVisibilityData::Update(bool)` (1122344 = 0x1427AF6C0; called from `Main::OnIdle`+0x111, 502840+0x42 at the start of the frame's render, `TES::LoadInterior`) applies them: the set keeps a **raw pointer** (adding a present key or removing a missing one does nothing), each processed object goes through `NiObjectGarbage::Add`, and the pending reference is released. So a registrant keeps the object alive while it is registered; after `Unregister` the queue holds it. `ClearCurrentVisibilityData` (360955) does not touch the set.
- **Who registers.** `TESObjectCELL::AttachReference3D` (+0x757, +0x82E) calls `TESObjectREFR::RegisterWithPrecomputedVisibility` (0x140401640). For a reference with 3D in a loaded cell, `TESObjectREFR::UsesStaticVisibility` (0x140401550: not a created form, and its form id is in the parent cell's extra data 0x15 hash set, the cell's previs references) means only door state is set. Otherwise (not the player's 3D, not a marker; a light registers its light with a visibility callback) the 3D is registered as a dynamic object and `UpdateIDto3DMap(id, null)` drops it from the id map. Other registrants: LAND, water, the portal graph (`TESObjectCELL::AttachToPortalGraph`+0x281), temp effects, projectiles, muzzle flashes. `UnregisterFromPrecomputedVisibility`, cell detach and `FreeLoadedData` unregister.
- **When bit 42 means "previs's main view".** 449607 writes a registered object's bit 42 inside the query (`Render_PreUI`+0x80), so read on return from that call it is previs's main-view verdict for the frame. Later passes rewrite it before the game tick: Runtime Combiner run 9 (2026-10-04, CBRO loaded, previs off, a lamp-lit interior) read it set on 16 chunk fade nodes in 60+ ticks that the main view never drew and that were off screen. Which pass set it is not traced; presumably group 0's finish loop (5.2), whose +0x169 stays set for every pass that processes group 0 (the lamp loop's slot-9 culls, CBRO's), not only the main view's.
- **Consequence: with precombines off, nearly every static reference is a dynamic object**, not an id in the per-frame lists. Runtime Combiner run 7 (2026-10-03, FOLINTBromleyDomsCafe, previs active, CBRO off): the main list held 76-85 ids a frame while the cell's 258 combinable references were drawn; chunks fed by those ids covered 2 of 62. Anything filed only in group 0 is undrawn while previs is active (5.3); registered as a dynamic object, it is drawn in all three views like a reference's 3D, culled by Umbra, its fade node faded by the main view.
- **Measured cost** (Runtime Combiner run 13, 2026-10-05, CBRO classic, GoodneighborExt, 25 exterior cells, a still view): the query (`Render_PreUI`+0x80, timed around the call) took **8.42 ms a frame** with precombines off and Runtime Combiner's 9,991 chunks registered beside ~24k hidden (AppCulled) originals, **8.08 ms** with precombines off and the originals shown, **0.07 ms** with precombines on: 20 ms vs about 11 ms a frame. The AppCulled skip does not make an entry free. The set's table (+0x88) has CommonLibF4's `BSTScatterTable` layout, so `RE::BSTSet<NiAVObject*>::contains` reads it on the main thread.
- Run 14 (same view): with the 24,189 hidden roots taken out of the set (20,829 objects left: 9,991 chunk fade nodes and ~10.8k references), the query took **5.38 ms**; with precombines on the set held 3,570 objects and took 0.135 ms. Per object that is ~258 ns against ~38 ns: a visible fade node (Umbra test, `OnVisible`, the geomArray walk, in three passes) costs far more than vanilla's mostly small dynamic objects.
- **The test recurses, and its cost is per registered object** (2026-10-05, Ghidra decompile of 1383851, for Runtime Combiner). A visible object that is not a top fade node (bit 14 + `IsFadeNode`) and is a node with children calls 1383851 on each child: every child gets the AppCulled and radius checks and its own Umbra AABB test (29920), so a registered node culls its subtree hierarchically; a node without children or a non-node is pushed as `{object, 0}`. Measured (Runtime Combiner runs 20 and 21, GoodneighborExt, same still view, CBRO classic): the query took about 0.4 us per registered object over its three passes, 1.37 ms for 3,566 (precombines on), 2.24 ms for 5,738 and 2.25 ms for 5,691 (precombines off, 927 and 881 chunk groups registered); what the visible groups held (22,473 vs 19,042 chunks, 55 vs 80 groups found visible) did not show.
- **Why precombines off makes references dynamic:** `UsesStaticVisibility` (1171499) reads only the cell's extra 0x15 (`ExtraPreVisRefs`, kCellPrevisRefs; built from the cell's XPRI subrecord by id 39694, loaded when byte id 925009 is set or the cell's file is a master, independent of `bUseCombinedObjects`). XPRI lists the references previs tracks one by one; precombined references are not in it (previs covers them through the precombined meshes), so with precombines off each of them gets 3D and becomes a dynamic object (25 GoodneighborExt cells: 35,762 dynamic objects off vs 3,570 on).

- **Layouts:**

- **Vertex layout** (`BSGraphics::Utility::UnpackVertexData` 0x141D2A450): the attribute a's offset is `(desc >> (4a+2)) & 0x3C`. - **The scene walk** skips an AppCulled child of a cell's child 3 before `Group::Add` (`test byte [rsi+0x108], 1` at 0x14284E532). So a hidden reference root costs one loop step.
- **A fade node is culled through its flattened geometry list.** `BSCullingGroup::AddP1FadeNode` (0x141CD0920) first calls `BSFadeNode::AtomicUpdateGeomArray(true)` (0x1427D25F0).   - The builder (visitor 0x1427D3340) sets an entry's bit 0 when the mesh or any node between it and the fade node is AppCulled, and bit 1 from the mesh's AlwaysDraw bit 11.

  - `F4SEPlugin_Load` ran on one thread, `kGameDataReady` on a second, and `kPreLoadGame` / `kPostLoadGame` plus every `CellAttachDetachEvent` and `TESObjectLoadedEvent` during the load screen on a third (the loader).

- **Per-frame hook:** `PlayerCharacter` vtable (0x142D438E8) slot 0xCF is `PlayerCharacter::Update(float)` (0x140E9D530, calls `Actor::Update` 0x140D7B020, the `Actor` vtable's slot 0xCF).

### 7.7 Input layouts and full-precision positions (2026-10-02 Ghidra, for Runtime Combiner)
- **Layout builder** (id 578780 = 0x141D15E90) turns a key (VS input mask & desc) into `D3D11_INPUT_ELEMENT_DESC`s and calls `ID3D11Device::CreateInputLayout` (vtable +0x58) with the current VS bytecode.
  - POSITION0 is always element 0 at **offset 0** (the position-offset nibble is ignored). Format R32G32B32A32_FLOAT when key bits 44 and 54 are both set (VF_FULLPREC), R16G16B16A16_FLOAT when only bit 44 is set. 4 components either way, so position w (bitangent x, 7.6) is read as a float in full precision.
  - Every other attribute takes its offset from the desc nibble: TEXCOORD0 R16G16_FLOAT, TEXCOORD1 R16G16B16A16_FLOAT, NORMAL / BINORMAL / COLOR R8G8B8A8_UNORM, skin, land and eye data, per-instance TEXCOORD4-7. Attribute a uses bit 44+a for slot 0, bit 54+a for slot 1.
- **Cache:** `SetDirtyStates` (id 1557284 = 0x141D16C00) keys on VS +0x60 mask & the state desc (renderer state +0x21F0), CRC32 lookup in a `BSTHashMap<u64, ID3D11InputLayout*>` at renderer data +0x2FB8; a miss calls 578780. So a full-precision desc gets its own layout.
- **Draw:** `DrawTriShape` (id 763320 = 0x141D0BFB0) sets the state desc from TriShape +0, `IASetVertexBuffers` stride = `(desc & 0xF) * 4`, offset = Buffer +0x48, R16_UINT indices. The explicit-desc draw (id 1240292) computes the stride the same way.
- **Shaders:** a VS's input mask (+0x60) is read from the package (`CreateVertexShaderFromStream` 0x141D10580). The shipped `Fallout4 - Shaders.ba2` (one file, `ShadersFX\Shaders011.fxp`) has 1,335 vertex shaders; all 1,255 that read POSITION keep bits 44 and 54 in their mask. A replacement package whose masks drop bit 54 would read float positions as halves.
- **Techniques:** `BSLightingShaderProperty` technique selection (id 1485318) reads the geometry desc only for eye data (gated by shader flag 0x400); the utility/shadow pass builder (id 757582) does not read it. VF_FULLPREC needs no extra permutation.
- Other layout callers (occlusion-query replay in id 1491502; ids 901559, 767228, 695145) keep bit 54 in their keys.
- **Precision helper:** `BSGeometry::CalculateVertexAttributeStreamExt(desc, attr)` (0x140261A40) returns 1 (float) when bits 54+attr and 44+attr are both set or both clear. Only seven functions load the mask 0x40100000000000 (full-binary scan): the layout builder, 0x141D19400, `BuildTriShapeData`, `BuildMergeInstancedTriShapeData`, NiPick's triangle test (id 841164 = 0x141D28CA0), `LoadingMenu` model code (id 16126) and id 894772. No code tests the flag by shift or byte test.
- **CPU readers of a static mesh's vertices** (callers of `Renderer::GetTriShapeDataAccess` 0x141D0DD30 / 0x141D0DD70 and `Utility::GetTriShapeDataAccess` 0x141D2C2A0):
  - precision-aware: NiPick (picking reaches cell geometry), `TESBoundObject::CalcBoundingBoxRecursive` (0x140324B10, a base object's 3D), ids 16126 and 894772.
  - **halves only, unchecked:** `BSGraphics::Utility::UnpackVertexData` (0x141D2A450; only caller `BSDismember::ExtractVertexData`, actor dismemberment), id 591076 (0x14128F200; `Inventory3DManager` item 3D), `CreatePositionData` (0x1401CCAB0; `BSMagicShaderParticles` on an effect target's 3D).
  - skinned / dynamic / FaceGen / cloth code, `BSTriShape::SaveBinary` (raw copy with the desc stride), the PSG builder and `BSMeshCombiner`. No Havok shape builder, occlusion or previs code reads render vertices.
  - Decals: `BSTempEffectGeometryDecal::DecalProjection` (0x140730DE0) is skinned decals only (`ProcessQueuedSkinnedDecals`); static decals read no vertices.
- **Engine precedent:** `BSMeshCombiner::CombineSameFormat` (0x14283BA20, via `DoCombine` 0x14283B6A0 from `BGSStaticCollection::Build3D` and others) widens to full precision exactly this way when the position offset is 0: bit 54 set, stride +8, every present attribute offset +8.
- **`BSLightingShader::SetupGeometry`** (vtable 343833 slot 7 = 1163207 = 0x14289DD10, decompiled 2026-10-03) takes the pass's geometry (+0x18) and property (+0x10) and reads only the geometry's current world transform (+0x70..+0xAC) for the matrices (helpers 652814, 1105055, 768946, 465796); `previousWorld` (+0xC0) is not read there, so a static mesh's stale `previousWorld` doesn't feed its motion vectors through this path. The deferred pre-pass does read it (7.10). A pass with technique byte +0x4C == 10 sets an alpha/stencil reference from the property's fade node: `currentFade` (+0x1A0), or +0x13C for a cross-fade pass (+0x4E bit 7), times 1529856 (the dithered fade).
- **Command buffers snapshot the format.** The `BSLightingShaderProperty` pass builders (ids 1485318, 2989, 757582, 1154768, 1486861) create command buffers through id 833764 (0x1428911F0) → id 695145 (0x141D146B0), which copies the masked desc, its input layout, the stride and the two ID3D11Buffers (taking refs) from the geometry's current renderer data. Passes live in the property's +0x38 list and are built when a visible geometry is accumulated. `BSGeometry::SetRendererData` does not clear them: swapping renderer data on a shape that has been drawn needs `BSShaderProperty::ClearRenderPasses` (0x1427BC4C0). A fresh clone (its own property, no pass list, 7.6) swapped before attach is safe.
- **Consequence:** a static `BSTriShape` can be given float positions by creating its TriShape with VF_FULLPREC set, stride +8 and every attribute offset after the position +8. The engine's own precombine baker keeps halves (7.6).

### 7.8 Fade nodes and the shader property's alpha (2026-10-03 Ghidra, for Runtime Combiner)
- **`BSShaderProperty` +0x28 is a draw-time cache, not a script alpha.** The `BSLightingShaderProperty` pass builders (id 1485318 = 0x1427CD790, store at +0x441, render modes 0x18 / 0x12; id 2989 = 0x1427CE4E0 for modes 0 / 0x15) compute alpha = material alpha (property +0x58 -> material +0x80, capped at 1 when the geometry has no `NiAlphaProperty` +0x130) x fade x property +0x64 (LOD fade). Fade = the fade node at property +0x48: `currentFade` +0x1A0, or `currentDecalFade` +0x1A4 x a decal LOD factor when shader flags & 0xC000000; 1.0 when accumulator +0xB0 is set. The result goes to +0x28, and +0x2C is reset to 0x7FFFFFFF when it changed. Alpha < 1 selects the blended path.
  - Shadow modes (0xF, 0x10, 0x11) don't write it. With fading on, `currentFade == 0` and node flag bit 15 clear, no passes are built and +0x28 is left as it was.
  - So +0x28 changes only while the mesh is drawn: an AppCulled, off-screen or filtered-out mesh keeps its last value. The constructor (0x1427BB950) sets +0x28 = 1, +0x64 = 1, +0x2C = 0x7FFFFFFF and +0x48 = the default fade object (id 244120, pointer 0x146721A28). `CopyMembers` (id 791618) copies +0x28 (possibly a stale partial value) but not +0x48 or +0x64.
  - Effect shaders: their pass builder (id 1289086) writes +0x28 through the setter id 280821 (0x1427BC430).
- **Persistent translucency** lives elsewhere:
  - material alpha: `BSLightingShaderProperty` vtable 241915 slot +0x190 sets material +0x80 (id 948445), +0x198 gets it (id 1134897). `BSShaderUtil::SetMaterialAlpha(node, alpha, onlyIfLower)` (id 211260 = 0x14281A880; lambda id 1116508 gives the property its own material first) is called by `TESObjectREFR::Load3D` (alpha 0 for primitives when `bPrimitivesOn` is 0), Sky statics, `BGShkMatFadeController` (id 818339, animated), a `BSTempEffect` (id 1086358) and the VATS / Build-a-Bot highlights. None runs per frame on ordinary STAT/SCOL references.
  - LOD fade +0x64: only `BGSDistantObjectBlock::UpdateLODFade` (id 912622, object-LOD blocks) writes it besides the constructor.
  - actors: Papyrus `Actor.SetAlpha` (id 1251510; FO4 has **no** `ObjectReference.SetAlpha`) -> AIProcess alpha -> `Actor::UpdateAlpha` (id 76565) -> fade node `fadeAmount` (`NiAVObject` +0x118).
- **`BSFadeNode` state.** `Init` (id 1211707 = 0x1427D0AB0, run by both constructors, ids 668955 / 309452) sets `currentFade` and `currentDecalFade` to 0 and clears flag **bit 37 ("fade complete")** when the fade-enabled byte 0x1438C4E44 (id 1220201) is set; otherwise 1 and bit 37 set. It also sets `frameCounter` +0x1B0 = 0, `previousMaxA` +0x1B4 = 1, near / far +0x198 / +0x19C = FLT_MAX and the LOD-mult type +0x11C = 0. `CopyMembers` (id 762200) clears bits 15, 37 and 49, copies near / far / type, and not `currentFade`: every newly loaded or cloned reference 3D fades in from 0.
- **Advance.** `BSFadeNode::OnVisible` (id 531348 = 0x1427D1000; gated by byte 0x1438C4E45, id 1445134) stamps `frameCounter` = the frame number (0x1438C4E6C, id 734919).
  - Type 6 (set by `SetLODMultType` 0x1427D1D40 when the world-bound radius is above 2048: the OC fade-node helpers ids 303341 / 546635 test it after an Update; `LoadTask::ProcessTriShape` tests it at 0x14036CECD before any Update, so precombined chunks stay type 0, 7.9) only fades in: `currentFade += min(frameDelta / fFadeInTime, 0.1)`, bit 37 at 1. `frameDelta` is 0x146721B9C (id 160595); `fFadeInTime` is 0x1438C4E48 (id 538734; `TES::TES` copies `fFadeInTime:LOD`, id 351311, default 1.2); the cap is 0x1438C4E68 (id 1415799). About 1.2 s of visible frames.
  - Other types (`TES::GetLODMult` 0x1400FEAD0: 1 for most bases, 2 for items and some others, 3 for NPC_) go through id 928617 (0x1427D1370). It takes `ComputeFadeAmount` (id 1040250 = 0x1427D2710) from camera distance and fades in above `fFadeInThreshold` 0.7 (0x1438C4E50), out below `fFadeOutThreshold` 0.3 (0x1438C4E54), out at `fFadeOutTime` 2.0 (0x1438C4E4C). A node unseen for over 20 frames with radius +0x1A8 below 600 snaps to 1 when near and restarts from 0 when far. It also moves `currentFade` toward `fadeAmount` +0x118 (a target above 1.5 means "set to target - 2 now").
- **Only visible nodes advance.** The finish loop 558046 (and lambda id 99288) calls `OnVisible` when the culling group's byte +0x169 is set (the main view's groups; set by the scene walk 1138818 and DrawWorld cull 718911), else `OnVisibleFadeInOnly` (id 1460815 = 0x1427D1310: snaps to 1 a node not complete and unseen by the main view for over 20 frames). It then calls `AddP1FadeNode` only when the node is not AppCulled, `fadeAmount` > 0, and bit 15 is set, fading is off or `currentFade` > 0. So an off-screen node keeps a partial fade, and an AppCulled reference root freezes (the walk skips it, 7.6).
- **Snaps that skip the fade:** `TESObjectCELL::UpdateFadeNodes` (id 332662 = 0x1403B6160) sets every reference 3D of the cell and the cell's +0xD0 list to 1 with bit 37; it runs after a save load (`BGSSaveLoadManager::EndLoadGame` via id 1488520). `SkipVisibleDistantFadeForLoadedCells` (id 889590 = 0x1403BE790) does the same for VisibleDistant references (`TES::HideLoadingMenu`, door arrival, `EndLoadGame`). Cells attached while walking fade in.
- `ConfigureFadeNodeRange` (0x1401CFAC0) sets a fade range from `uGrids * 4096 / 2 - (radius + 2048)`, capped by a multiple of the radius (callers not traced yet).
- The fade-node culler slot (id 1582278 = 0x1428844F0) only tests the bound against 6 planes (culler +0x3C), sets bit 26 and sets or clears NotVisible bit 39. id 1234977 (0x140E92F70) probes a reference's 3D and writes reference +0x484 (bit 0 tested, bit 1 not occluded, bit 2 `currentFade` >= 1e-5).
- **Measured (Runtime Combiner run 3, 2026-10-03):** about 0.7 s after a cell attached while walking, up to 99 meshes per cell had +0x28 < 1; across rebuilds over the next 90 s the count fell 97, 19, 19, 11, 1 as the player looked around (stale caches of meshes last drawn mid-fade).

### 7.9 How a precombined chunk's `BSFadeNode` is built, and its fade range (2026-10-03 Ghidra, for Runtime Combiner)
- **Construction.** `BSFadeNode::BSFadeNode()` is id 668955 (0x1427D04C0, `this` only: `NiNode(this, 0)`, vtable, +0x140 = -1, +0x144 = 0, the arrays, then `Init`). id 309452 (0x1427D0560) is `BSFadeNode(NiNode* src)`, a conversion (name, flag bits 10 and 12, children; used by `BSModelDB::DBTraits::Create`, `TESBoundObject::CloneLoadedGraphics`, `BSLeafAnimNode`). Allocation: `MemoryManager::Allocate(0x1C0, 0x10, true)` (= `RE::aligned_alloc(0x10, 0x1C0)`). VTABLE 93613 = 0x143085EE8, NiRTTI 1168275, RTTI 35452; destructor 1131839. Vtable: +0x30 `IsFadeNode`, +0x180 `UpdateDownwardPass` (753151), +0x1A8 `UpdateTransformAndBounds`, +0x1C8 `OnVisible`, +0x210 upward pass (472974: with bit 14 set it only updates its own world bound); +0x1D0 is plain `NiNode::AttachChild` (273401: parent link and child array only, no flags or bounds).
- `Init` (7.8) also sets +0x11E = 1 (3 when fading is off or 0x1438C4FC0 is set), +0x1A8 / +0x1AC = 0, clears bits 15 and 49, +0x1B8 = 0, +0x13C = 1.0, +0x11F = 0xF, +0x11D = 2, and `flags |= 0x100004000` (bit 14 "top fade node" and bit 32).
- **`LoadTask::ProcessTriShape`** (id 1050164 = 0x14036CC50, loader thread), per precombined chunk: allocate and construct (a `BSLeafAnimNode`, 0x1E0, for tree-anim shaders); `flags |= bit 44` when byte 0x1458E3F28 is 0 (no writer); clone or bake the shape (`BuildTriShapeData` also pushes each instance's world bound into `mergedGeomBounds` +0x180, which nothing found reads); `AttachChild(shape)`; copy the shape's bit 12; `if (+0xBC > 2048) SetLODMultType(6)` (reads 0: no Update yet); `ConfigureFadeNodeRange(node, (float)uGridsToLoad, false)`; `StoreClone` (1181944); `PostBuildTriShape` (974289) runs `NiAVObject::Update(node)`.
- **`ConfigureFadeNodeRange`** (id 1417061 = 0x1401CFAC0, `(BSFadeNode*, float uGrids, bool noCap)`): type 10 gives R = 150000. Otherwise r = world-bound radius +0xBC, or half the z of the BBX extra data when r < 0.001 (0 without one); R = uGrids * 4096 * 0.5 - (r + 2048), and unless noCap or r == 0, R = min(R, `fLODBoundRadiusMult:LOD` (default 10) * r). Then `SetRange` (id 1164193 = 0x1427D1CF0) with near = `fLODFadeOutPercent:LOD` (id 648127, 0.6) * R, far = R; near is raised to at least 500 (0x1438C4EA0), and then far to at least 1000. `uGridsToLoad` is the int at 0x1436D9B50 (id 504589).
  - **Every reference root gets its own range** (dumpbin 2026-10-03): `TESObjectCELL::AttachReference3D` +0xE5F (0x1403E0EEF) calls it for the root `BSFadeNode` (flag bit 14) with uGridsToLoad, or the float at 0x1436E9B88 when the cell's flag bit 13 is set (then noCap is set too); when the base object's vfunc +0x2A8 is true the type becomes 10 first. Other callers: `TESObjectREFR::AttachToParentRef3D`, `AttachAllChildRef3D`, 957936, `ProcessTriShape`, the OC helpers 303341 / 546635. So small references fade out at 10 x their radius (s units), large ones near the loaded grid's edge.
  - `SetRange` (1164193) only writes near +0x198 (at least 500) and far +0x19C (at least 1000 when near was raised).
  - In game units, a node starts fading at `fDistanceMultiplier:LOD` (515159 = 0x1438C4E64) x near x mult(type) / lodAdjust (camera +0x194), mult from the table 804710 (0x1438C4E18); the fading byte is 1220201 (0x1438C4E44).
  - **Every precombined chunk at uGrids 5 gets near 4915.2, far 8192**, whatever its radius (the range is taken before the first Update, with r = 0).
- **`ComputeFadeAmount`** (id 1040250): mult = the table at 0x1438C4E18 (id 804710) indexed by type +0x11C; k = `NiCamera` +0x194 (lodAdjust = FOV / 80, `BSShaderUtil::SetCameraFOV` 1463640) / mult, or 0.2 when mult <= 0 (and a type other than 6 snaps to 1). s = k * distance from the node's world-bound centre to the camera. near and far are scaled by `fDistanceMultiplier:LOD` (0x1438C4E64, default 1). It returns 1 when s <= near or fading is off, else 1 - (s - near) / (far - near), unclamped. It also sets +0x1BC = old +0x1B8 and +0x1B8 = s / 7200.
  - The table (`TES::InitFadeOutMultipliers` 0x1400FECC0): types 0, 1, 4, 5, 8 = `fLODFadeOutMultObjects:LOD` (default 4.5); 2 = `fLODFadeOutMultItems` (2.5); 3 = `fLODFadeOutMultActors` (6.0) times a player value; 10 = `fLODFadeOutMultSkyCell` (1.0); `TES::TES` sets 6 = 0 and 7 = -1.
  - So a precombined chunk (type 0) starts fading out at about 4915 * 4.5 / lodAdjust, roughly 20-22k units, and is gone at 33-37k: beyond the loaded uGrids-5 area. **Precombined chunks practically never distance-fade**; their visible fade is the fade-in after attach.
- **`boundRadius` +0x1A8** is written only by `Init` (0) and `CheckFadeRadius` (632323, called for reference roots from `TESObjectCELL::AttachToWorldRefHelper` and `TESObjectREFR::Load3D`). Precombined chunk nodes keep 0, so the 20-frame unseen rule of id 928617 (7.8) always applies to them.
- **The geometry list builds itself.** `NiAVObject::Update` (121052) calls vtable +0x180. `BSFadeNode::UpdateDownwardPass` (fade depth 1 in the update data +0x18) runs `NiNode::UpdateDownwardPass`, then compares the geometry count (update data +0x14, incremented by `BSGeometry::UpdateDownwardPass` 195475) with `geomArray`'s; when they differ or bit 29 is set it runs `ComputeGeomArray` (1465474), else `MergeWorldBounds` (1012658). It copies update-data bit 21 (shader flag 62 seen) into node bit 33. Nothing sets bit 29 on a fresh node, and nothing needs to: the first Update finds 1 != 0.
  - `ComputeGeomArray`: clear, set node bit 14, run the visitor (7.6), clear bit 29, then `MergeWorldBounds` (world bound = the merged entries' bounds). Without an Update the node has radius 0 and an empty list and draws nothing.
- **Attaching precombines** (`AttachCombinedObjectArt` 1491658 -> per source geometry, lambda 95264 = 0x1403CA2C0): looks up the stored fade node and attaches it to loadedData +0x1E0 (`CombinedObjectNode` 362100), to cell child 9 for mesh keys with bit 30, to a multibound / portal node in interiors, or to the portal graph's always-render list. ### 7.10 Motion vectors come from `previousWorld`, through the deferred pre-pass (2026-10-03 Ghidra, for Runtime Combiner)
- **`BSDFPrePassShader::SetupGeometry`** (vtable 1091304 slot 7 = id 478025 = 0x142863C20; pass geometry at +0x18) loads two VS constants for every technique without bit 2 of the shader's +0x118 (the other branch handles bone data): the geometry's **world** (+0x70..+0xAC, rotation rows times scale, untranslated by the camera) into slot `id_430541`+0x69, and its **`previousWorld`** (+0xC0..+0xFC) likewise into +0x6A. The pre-pass draws the velocity that TAA (`sAntiAliasing=TAA`) and motion blur reproject with. `BSLightingShader::SetupGeometry` reads only the world (7.7).
- **`NiAVObject::UpdateWorldData`** (850280 = 0x141BA40F0), the transform step of every `Update`: without a collision object driving it, it first copies world (+0x70..+0xAC) into `previousWorld` (+0xC0..+0xFC), then computes world = parent world x local (or the parent's world when flag bit 45 is set). So `previousWorld` is the world before the last update. A static object updated once after it is built keeps a stale one, and its velocity points back to where it was before placement; a second update with nothing moved makes them equal.
- **Observed** (Runtime Combiner run 8, 2026-10-03, TAA on): with chunks updated once after cloning, the user saw a translucent, zoomed-in copy of the frame over the scene, caused by Runtime Combiner. The fix (`previousWorld` = world after the update) awaits a run.
- Correction: 7.7's "`previousWorld` is not read there" holds for the lighting shader only. Runtime Combiner's run-6 conclusion "motion vectors ruled out" was wrong for any mesh whose `previousWorld` differs from its world.

### 7.11 `BSMeshLODTriShape`: mesh LOD segments (2026-10-05 Ghidra, for Runtime Combiner)
- Layout: a `BSTriShape` (0x170 bytes) plus `u32 lodSizes[3]` at +0x170 (object 0x180; vtable 403494 = 0x14309BB68, NiRTTI 1000858). Type byte +0x158 is **5** (`BSTriShape` 3). Its constructors (`BSMeshLODTriShape(BSTriShape*)` 1331814 = 0x1428E1B40, `CreateClone` 362115 = 0x1428BCDF0) set flag bit 12 (0x1000, the mesh-LOD flag). `LoadBinary` (959987) is `BSTriShape::LoadBinary` and then reads the 12 bytes, so +0x160 holds all triangles.
- Vtable against `BSTriShape`'s (183326 = 0x142E16AE8): only slots 0 (destructor: `~BSTriShape` then the same `MemoryManager::Deallocate`), 2 (GetRTTI), 26-31 (CreateClone, LoadBinary, LinkObject, RegisterStreamables, SaveBinary, IsEqual), 57 (`OnVisible`, 1091434) and 65 (1428BD1F0) differ. The extra fields are plain data.
- `GetNumPrimitivesAtLodMode(mode)` (307173 = 0x1428BD270): `mode | 0x80` gives segment `lodSizes[mode]` alone; otherwise the sum of the first `mode` segments. **The segments are cumulative from index 0**: level 1 draws the first lod0 triangles, level 3 all lod0 + lod1 + lod2.
- The level is the owning fade node's byte +0x11E (the shader property's +0x48 fade node), set by `BSFadeNode::DetermineMeshLODLevel(distance)` (980443): 3 (full) near or with the mesh-LOD switch (id 88157) off, 2 at middle distance, 1 far. `OnVisible` skips the mesh when that count is 0. The render pass setup (id 833764, 0x14289132D) takes the index count from `GetNumPrimitivesAtLodMode` when type byte +0x158 is 5, else from +0x160.
- `BSMeshCombiner::AddLODTriShape` (1526332) adds each non-empty segment as its own piece, index start advancing by `size * 3`.
- `BSTriShape::CreateClone` (773581 = 0x141BB5FA0) allocates 0x170 bytes, runs `BSGeometry`'s constructor, sets type byte 3 and the vtable, then `BSTriShape::CopyMembers`. `NiObject::Clone(void)` (604942) is CreateClone (slot 26) then ProcessClone (slot 32) through a stack `NiCloningProcess`.
- Runtime Combiner use: combine the first lod0 + lod1 + lod2 triangles (full detail). A chunk cloned from such a mesh is turned into a plain `BSTriShape` (vtable, type byte 3, flag bit 12 cleared), so it draws +0x160 triangles at every distance.

### 7.12 The precombine switch's readers and the cell's precombine art (2026-10-05 Ghidra, for Runtime Combiner)
- The 12 reads of `bUseCombinedObjects` (0x1436E9C00, 7.6): `TESObjectCELL::IsCombinedObjectRef` (350700), `AttachCombinedObjectArt` (1491658), `QueueCombinedObjectArt` (1411559), `UnLoadAllTempData`+0xEE, both `ForEachCombinedRef` instances (127642, 1457748), `AddReference`+0xE1, `InitItem`+0x169, `BGSCombinedCellGeometryDB::LoadTask::ProcessTriShape`+0x18 and `TryFinish`+0x54, id 1336932+0x51, id 664626+0x6. `DetachCombinedObjectArt` (1408530) does not read it itself.
- `IsCombinedObjectRef(cell, ref)`: false with the switch off; else looks the ref's form id up in the cell's extra data 0xC5 (a hash of the precombined refs' form ids).
- `QueueCombinedObjectArt(cell)`: with the switch on, `BGSCombinedCellGeometryDB::UpdateRequest(loadedData+0x188, loadedData+0x190, cell, priority)` queues the cell's precombined NIFs; with no request left, loadedData+0x210 = 1 (`HasAttachedCombinedObjects` reads +0x210). Callers: `AttachModels`, `QueueReferences`, a grid `ForEachCell`, two script paths. `LoadTask::TryFinish` then calls `AttachCombinedObjectArt`, as do `TES::GridArrayLoad`, `TESObjectCELL::AttachToWorld` and `TES::LoadInterior`.
- `AttachCombinedObjectArt` attaches the chunks, adds the combined collision (`bhkWorld::AddObjects`), updates the node, and adds every precombined ref to `BGSObjectVisibilityManager` (`ForEachCombinedRef` 127642, `AddReference`). It does not touch the refs' own 3D: precombined refs skip their 3D when they load.
- `DetachCombinedObjectArt` (callers `GridCellArray::PerformQueuedCellAttachDetach`, `TESObjectCELL::Detach`) removes them again through `ForEachCombinedRef` 1457748, which runs only with the switch on.
- Consequence: a cell attached under one value of the switch and detached under the other leaves the visibility manager unbalanced (on to off: refs left registered). Runtime Combiner writes it at `kGameDataReady` (no cell loaded yet) and at the game reset below.
- **How precombined chunks reach previs** (`RegisterCombinedObjectVisibility` 1274329, 2026-10-05 Ghidra): once per attached cell (loadedData +0x216 guards it), for each entry of loadedData +0xC0 (count +0xD0) that has flag bit 14 and is a fade node, `BSPreCulledObjects::UpdateIDto3DMap(id, node)` with the synthetic id `0xFD000000 | (((cellX & 31) << 5 | (cellY & 31)) << 14) | (index & 0x3FFF)`, index counting only those entries. `UnregisterCombinedObjectVisibility` (728859) walks the same list. So the tome returns 0xFD ids for visible precombined chunks, mapped by their order in the loaded art: a runtime replacement can't use those ids without loading the precombined NIFs.
- **The precombined reference list exists with precombines off** (2026-10-05 Ghidra): the cell loader (id 39694) builds extra 0xC5 (`ExtraCombinedRefs`, vtable 130663, ctor 520544, 0x90 bytes) from the cell's XCRI subrecord whenever byte id 925009 is set or the cell's file is a master, the same condition as XPRI and independent of `bUseCombinedObjects`. +0x18 is a `BSTSet<u32>` of the precombined references' form ids (capacity +0x24, sentinel +0x30, entries +0x40: what `AddReference` and `IsCombinedObjectRef` look up), +0x48 a `BSTArray<u32>` of the combined meshes' hashes. Runtime Combiner reads the set (`RE::BSTSet<std::uint32_t>::contains`, main thread, after `ExtraDataList::GetByType` under the list's lock) to give those references the precombined chunks' fade instead of their own.
- `TESObjectCELL::ReAddCombinedObjectRefs` (1214859) is called by `LoadAllTempData`, `ClearPreCalcedData`, `InitItem` and id 634071. It was not read.
- **`TESObjectCELL::AddReference`+0xE1 sorts references by the switch when the cell's data loads:** with it on, a non-persistent ref listed in extra 0xC5 is not added to the cell's reference list but to a set inside that extra (+0x68), so it never gets 3D; with it off it is an ordinary reference. `InitItem`+0x169 with the switch on calls `ReAddCombinedObjectRefs` for a cell from a non-master file. So the split lasts as long as the cell's data does, buffered (detached, still loaded) cells included: one loaded under one value and attached under the other has holes (on to off: its precombined refs have neither art nor 3D) or draws twice (off to on: art plus the refs' own 3D).
- Exterior teleport (id 1581792, 0x14011B8C0, fast travel's path) calls `TES::PurgeBufferedCells` (+0x622 / +0xD8F) before it detaches the old grid (`Detach`, `ClearReference3D`, `Clear3D`), then `AttachToWorld` + `AttachModels` for the new one: the old grid stays in the buffer, so a fast travel is no safe point. `TES::LoadInterior` (1096651, +0x30F) and `TES::LeaveInterior` (1386854, +0x296) purge too; their order against the detach was not read.
- **`Main::PerformGameReset` (124452 = 0x140D3B800) runs `TES::ClearAllCells`, then `TES::PurgeBufferedCells` at +0x2ED (E8 call)**, before the save's world loads. Right after that call no cell is loaded: the one safe point to change the switch mid-session. Runtime Combiner hooks that call (2026-10-05) and writes F3's pending switch there.
